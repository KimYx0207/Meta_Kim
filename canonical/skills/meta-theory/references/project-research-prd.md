# Project context, research and one PRD authority

The order remains Critical -> Fetch -> Thinking -> Execution -> Review -> Meta-Review -> Verification -> Evolution. A bounded read-only project scan precedes Critical; it is not another stage. Its manifest/script declarations are evidence to inspect, not proof that a project builds, that a language is fully detected or that the host understood it. The packet records source hashes, module directories, declared versions, entry scripts, tracked/untracked worktree paths and explicit truncation/unavailability. Never run unknown project scripts just to classify a project. No manifests does not prove a directory is a new project: preserve `unclassified_existing_material` and inspect relevant files.

Use the existing requirements dialogue and decision frontier. Resolve inspectable facts yourself. Offer nontechnical users two or more real alternatives, a recommended outcome and concrete cost/maintenance/compatibility tradeoffs only for material choices. Continue discovering implications after an answer and retain earlier decision history. Research can change a recommendation; it cannot turn that recommendation or elapsed time into user approval. Thinking finishes the PRD and its task slices before formal workers are created.

## Research record

`requirementsDiscoveryInput.research` binds `schemaVersion:1`, the current `taskHash`, explicit `intentDigest` (or null), `required`, `topics` and `sources`. Full design (`designRequirement.required`) or explicit `research.required` requires three qualified repositories, with five as a target. A small bounded change may omit research where it cannot change a decision; this cannot override an explicit research request. Official documents do not inflate the GitHub count. A repository must be linked to a declared topic; unrelated entries in the source list do not count.

Each topic has `id`, `question`, `keywords`, `queries`, `sourceIds`, and optional `decisionRefs`. Each query records the declared `keyword`, `channel: "web"|"github"`, actual query text and `observedAt`. Search both channels per keyword, read the relevant original material, and deduplicate repeated queries. Each source has `id`, `kind: "github"|"official"`, public HTTPS `url`, `observedAt`, `relevance`, `findings`, and `adaptation`; GitHub sources additionally require observed integer `stars >=100` and a full 40-character commit `revision`. A source may declare `expiresAt`; expired selected evidence returns to Fetch. For changeable claims set an appropriate expiry and recheck them at use time. Metadata and a written summary alone do not authenticate external invocation or semantic relevance; the host must actually read the relevant source and Review must assess its fit.

The runner persists immutable `research-<digest>.json` files inside the trusted project artifact directory, rejecting path escapes, symlinks and changed existing bytes. Existing preparation artifacts retain the record during a user wait; later ordinary-entry calls recover research through the same requirements record. New evidence produces a new digest; older files and decision artifacts remain available. These records are evidence, not another PRD or task queue. PRD `researchRefs` summarize its basis and task slices select only their relevant IDs through `researchRefs`; a task with no relevant research requires a concrete `researchNotApplicableReason` when research is required. Unknown IDs, missing keyword channels, stale sources, insufficient qualified repositories and missing task bindings block readiness.

Workers receive selected `researchEvidence` entries containing a short finding, relevance, adaptation, URL/revision and `recordRef`/`recordSha256`/`researchDigest`. `readTaskResearchEvidence({projectRoot,evidence,taskHash,intentDigest})` validates the trusted path, current goal binding, immutable bytes, selected summary and source freshness before returning only the selected source entries. A source hash binds the record, not the truth of an external claim. Do not copy all research into every worker or create another task authority.

## Numerical acceptance

Use the existing structured `successCriteria` and `acceptanceCriteria`. A real numerical promise carries `criterion.measurement` with `kind`, `unit`, `scope`, `conditions`, `comparison`, `target`, optional `minimumSamples` and, for ratios, `expectedTotal`. Preserve this structure through intent evolution and PRD handoff. The host distinguishes performance/quality targets from incidental digits such as versions and phone numbers. Evaluators calculate counts, durations and ratios from samples, requiring each sample to meet the rule. Product outcome review additionally binds each sample's `evidenceRef` and `evidenceDigest` to an actual current artifact snapshot included in that observation. A supplied number or `pass` string is not measurement evidence or native execution proof.
