# Reviewed dependency baseline

`config/dependency-baseline.json` records the immutable Kim_Service commit, the
Graphify producer version and the digest of the npm dependency lock. It describes
the selected compatibility baseline. It does not prove that a user has installed
a dependency, granted permission or completed a native task.

## Installation and updates

- Ordinary and managed Graphify installation both use `graphifyy==0.9.56` from
  this configuration. Existing different versions are reconciled to that pin;
  installation is successful only after `pip show` reports the selected version.
  The public `graphify install` and `graphify update` entrypoints use the same
  reconciliation helper and stop before integration/Hook installation if the
  installed package does not match. The managed Python test launcher also reads
  this baseline instead of keeping a separate expected version.
  The managed runtime copies the baseline beside its manager and producer, so it
  remains usable after the original package or an npx cache has been removed.
- Remote Kim_Service installation fetches the exact commit from the baseline,
  checks out detached HEAD and verifies the revision and clean source before
  copying the indexed component closure. A source revision receipt is included
  in the immutable managed source. A newer branch HEAD is never substituted.
- `--prefer-local-dependencies` still uses the explicitly selected local source.
  Its receipt says `local_override`, with no claim that it matches the reviewed
  commit. Ordinary reruns retain that choice; an explicit update without a local
  override selects the reviewed remote commit. Older receipts without revision
  metadata remain readable for discovery, but are not treated as reviewed pins.
- ECC's optional non-Claude installer uses `ecc-universal@2.2.3`. Its default
  `upstreamHookPolicy: "disabled"` emits `--no-hooks`, including for OpenCode.
  An explicit `upstreamHookPolicy: "enabled"`, or a per-target entry in
  `upstreamHookPolicyByTarget`, emits upstream's `--enable-hooks`. This preserves
  the existing target selection and Codex user-configuration protection. Claude
  marketplace installation remains a separate upstream plugin path.

## npm and CI

`npm-shrinkwrap.json` is the single npm lock. It is generated by npm, included in
the package allow-list and consumed by `npm ci` and stable runtime installation. The
stable runtime installer maps its reviewed dependency identities to the outer
bundle's root lock, then uses `npm ci` for a fresh bundle. This avoids relying on
npm-version-dependent handling of a local tarball's nested shrinkwrap. A
package-lock that exists only in a checkout cannot pin installation of the
distributed tarball.

The baseline was resolved before `2026-11-10T00:00:00Z`, retaining the declared
Node 22.13.0 minimum. The November 10 Inquirer release requires a newer Node
patch. The current lock selects `@inquirer/prompts` 8.7.5,
`@modelcontextprotocol/sdk` 1.32.2 and `zod` 4.6.7. CI uses Node 22.13.0 for the
regression lanes and Node 24.22.1 for the existing DSH host lane. The two Service
checkout jobs read the same commit configuration as the installer. All ten
existing Node setup jobs in the CI, Graphify and runtime-evidence workflows read
their versions through `node scripts/dependency-baseline.mjs --github-output`.
That entrypoint validates the baseline before appending any workflow output.

A changed reviewed lock permits a fresh immutable runtime bundle. The previous
authoritative bundle must first pass its existing receipt checks, and is left
intact. The candidate is checked against every installed dependency's locked
version, source and integrity. Unchanged locks continue to preserve the existing
accepted dependency bytes. Changing a lock without updating the reviewed digest
fails before staging; a new lock cannot authorize tampered bytes in an old bundle.

To intentionally change this baseline, resolve and test the desired dependency
tree with npm, run `npm shrinkwrap`, and record the actual SHA-256 of those bytes
in the configuration. Validate `npm ci --engine-strict --ignore-scripts`, a real
packed installation, and the immutable-bundle update regression before accepting
the new digest. Do not edit integrity values by hand. A package version change
also needs the lock's root package metadata and reviewed digest refreshed.

## Packed verification prerequisites

Packed acceptance uses a disposable installation and user home. Official Claude
Code and Codex executables must be available on the test process's PATH; the
free `--version` probes establish executable availability only. They do not run
a model or grant execution authority.

Observation portability separately requires the existing exact set of ten fresh
original Claude Code/Codex `interactive_host` observations. Missing observations
are reported as `environment_unavailable`, with the missing identities retained
in the report. Test fixtures, CLI versions and imported advisory snapshots do
not satisfy this requirement. Completed install/update proofs remain visible,
but the standard release gate stays incomplete until its required observations
and remaining stages pass.

Execution-demand route smoke additionally needs an actual execution owner that
fits the task and runtime. The nine Meta governance roles are not execution
owners. A discovered read-only Service method or a skills-only plugin cannot
stand in for an engineering worker when the check asks for a code-producing
task. A missing owner is an explicit environment prerequisite; synthetic test
agents are useful contract fixtures, never evidence that the user's host has
that owner installed.

Read-only protocol diagnostics use the real prepare/Fetch/Thinking handshake.
Their source selections may be supplied through `diagnosticProviders` or the
JSON-valued `META_KIM_DIAGNOSTIC_PROVIDERS` environment setting. Selections name
the runtime and distinct source-bound execution/review providers; ambiguous,
missing, wrong-runtime or governance-only owners are rejected. Discovery and
planning do not prove that any selected provider was invoked.

Global reuse acceptance follows the public Critical → Fetch → Thinking protocol,
selects source-bound records returned by actual Fetch and checks all three Agent,
Skill and Command decisions. It verifies that reuse creates neither project
copies nor ownership entries. This is planning and file-ownership evidence; it
does not claim a worker or model executed.

## Desktop MCP qualification

The optional `agent-desktop` entry exposes upstream CLI, native stdio MCP
(`agent-desktop mcp`, version 1.2.0 or later), and C library interfaces. Discovery
only observes executable presence. Version, host registration, permission,
session, invocation and outcome remain unverified until the appropriate native
probe runs. Even a compatible observed version alone cannot make a candidate
eligible for execution.
